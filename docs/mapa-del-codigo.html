Las capas

Cada pedido del navegador entra por Flask, lo atiende una ruta, la ruta le pide a un servicio que aplique las reglas, el servicio lee o modifica los modelos y los modelos se guardan en SQLite. La ruta responde con una plantilla HTML o, si el pedido vino de JavaScript, con JSON.

Lo que se vePlantillas, CSS y JS. No toman decisiones: muestran datos y mandan pedidos.
RutasUna función por URL. Traducen el pedido (formulario o JSON) a una llamada a un servicio.
ServiciosLas reglas: si algo no se puede hacer, lanzan ErrorDeNegocio con el mensaje para el usuario.
ModelosLas clases que son tablas. La ruta hace el commit cuando todo salió bien.

Dónde vive cada cosa

Cada parte de la aplicación está en la zona de lo que usa. Lo que queda en el medio usa las tres cosas: JavaScript en el navegador, Python en el servidor y la base de datos. Tocá una etiqueta para ver por dónde viaja.

Solo JavaScriptPasa en el navegador con lo que ya está en la página. No le pregunta nada al servidor.
Solo PythonTrabajo del servidor que no necesita la base: armar el HTML, validar, dar formato.
Solo base de datosLas tablas. Están guardadas, pero nadie las lee directo: siempre a través de los modelos.
Las tresLas pantallas que trabajan sin recargar: el JS le pide al servidor, el servidor lee o cambia la base y responde.

Qué se conecta con qué

Elegí una caja para ver para qué sirve, qué funciones tiene y con qué partes se conecta. Las líneas van de izquierda a derecha: una pantalla llama a rutas, las rutas usan servicios y modelos.

Las URLs

Todas las direcciones que atiende la aplicación, agrupadas por blueprint. público no pide nada, login pide estar logueado, admin pide el rol administración y JSON son las que usa el JavaScript.

Base de datos

Seis tablas. Las líneas son las claves foráneas: un tipo tiene muchas habitaciones, una habitación tiene muchas reservas y un huésped puede tener muchas reservas.

La ocupación no se guarda La habitación solo guarda su estado físico (limpieza y mantenimiento). Si está libre u ocupada lo calcula services/ocupacion.py mirando las reservas de esa fecha.
Estados de una reserva confirmada → en_curso (check-in) → finalizada (check-out) cancelada y no_show no ocupan la habitación.
Fechas salida es el día del check-out: esa noche ya no se ocupa. Por eso uno puede salir y otro entrar el mismo día sin superponerse.

Tres recorridos de punta a punta

Qué archivos y funciones se usan, en orden, cuando pasa algo en la pantalla.

Un cliente reserva desde el sitio

Formulario común: el servidor responde con HTML.

  1. En la portada (sitio/inicio.html) elige fechas y personas: el buscador hace GET /reservar.
  2. routes/sitio.py → reservar() elige el tipo más barato donde entran y muestra sitio/reservar.html. reservar.js calcula el total mientras cambia los datos.
  3. Al confirmar hace POST /reservar y la ruta llama a reservas.crear_reserva_web(), que revisa el nombre y la capacidad y busca la primera habitación libre del tipo.
  4. crear_reserva() valida fechas, mantenimiento y superposición, calcula el total y crea la Reserva con su Huesped.
  5. La ruta hace db.session.commit() y redirige a /reserva/<token>. La reserva ya aparece en el plano y en el tape chart.

Recepción hace un check-in

JavaScript: la página no se recarga.

  1. Clic en una habitación: plano.js pide GET /administracion/plano/habitaciones/<id> y pone el HTML de _panel.html en el panel.
  2. Botón «Hacer check-in»: postJSON() de app.js manda POST /administracion/api/reservas/<id>/check-in.
  3. api.checkin() llama a recepcion.hacer_checkin(): revisa que la reserva esté confirmada, que sea el día, que la habitación esté limpia y libre.
  4. Si algo falla, el servicio lanza ErrorDeNegocio y la API responde 409 con el mensaje: aparece un aviso rojo.
  5. Si sale bien hace el commit y responde {"ok": true, "mensaje": …}. plano.js pide /plano/contenido y reemplaza los indicadores y los pisos.

Recepción arrastra una reserva

Tape chart: arrastrar con el mouse o el dedo.

  1. tapechart.js escucha pointerdown y pointermove sobre la barra y calcula las fechas nuevas según cuántos días se movió.
  2. Mientras arrastra, motivoDeRechazo() revisa en pantalla si pisa otra reserva y lo muestra en el tooltip.
  3. Al soltar manda POST /administracion/api/reservas/<id>/mover con la habitación y las fechas.
  4. api.mover() llama a reservas.mover_reserva(), que vuelve a validar todo en el servidor y recalcula el total.
  5. tapechart.js pide /reservas/grilla (el HTML de _tape.html) y reemplaza la grilla sin perder el scroll.
