1

Conserje en 30 segundos

Conserje es un sistema para administrar un hotel, pensado para venderlo a muchos hoteles. Cada hotel le pone su nombre, su logo y su color, y el sistema se adapta. Tiene dos partes: la administración, donde la recepción ve qué habitaciones están ocupadas, hace el check-in y mueve reservas arrastrándolas, y el sitio público, donde un cliente ve las habitaciones en 3D y reserva. Cuando alguien reserva desde la web, la reserva aparece al instante en la administración.

Con qué está hecho: Python con Flask del lado del servidor, una base de datos SQLite, y del lado de la página HTML, CSS y JavaScript sin frameworks. Las habitaciones en 3D se modelaron en Blender. Lo único externo es Google Maps (el mapa del hotel), Google Fonts (la letra) y un visor 3D llamado model-viewer.

Usuarios para probar: admin@mirador.demo / admin123 (ve todo) y recepcion@mirador.demo / recepcion123 (no ve la configuración).

2

La idea general: funciona como un restaurante

Una aplicación web se entiende bien pensándola como un restaurante. Cada parte del código tiene un puesto, y cada puesto hace una sola cosa.

El cliente en la mesa

El navegador

Mira la carta (la página) y hace pedidos: «quiero ver el plano», «reservá la 204».

Es HTML, CSS y JavaScript.
El mozo

Las rutas

Toma el pedido, se lo lleva a la cocina y vuelve con el plato. No cocina: solo sabe a quién pedirle cada cosa.

Es app/routes/.
La cocina

Los servicios

Tienen las recetas, o sea las reglas: «no se puede hacer el check-in si la habitación está sucia». Si algo no se puede, avisan por qué.

Es app/services/.
La despensa

La base de datos

Donde se guardan las cosas en fichas ordenadas: habitaciones, reservas, huéspedes. Se usa a través de los modelos.

Es app/models/ y el archivo hotel.db.
El emplatado: las plantillasLa cocina prepara los datos y las plantillas (app/templates/) los ponen lindos en el plato: arman el HTML con el nombre del hotel, las habitaciones y los colores.
Lo que hacés sin llamar al mozo: JavaScriptFiltrar el plano o arrastrar una reserva pasa en la mesa, sin molestar a nadie. Cuando hace falta guardar algo, el JavaScript le pasa una notita al mozo (eso es un fetch con JSON) y espera la respuesta.
La regla más importante: el cliente nunca entra a la despensa. El navegador no toca la base de datos; siempre le pide a Python, y Python revisa las reglas antes de guardar. Así nadie puede saltearse una regla desde la página.

3

Una reserva, contada como historia

Seguir un solo ejemplo de punta a punta es la mejor forma de mostrar que las partes se conectan. Lucía quiere ir al Hotel Mirador del 20 al 23.

  1. Lucía entra al sitio del hotel, pone las fechas y 2 personas, y aprieta «Ver disponibilidad». el navegador pide la página /reservar.
  2. El mozo (la ruta) le arma la página de reserva con la habitación más barata donde entran dos personas. Mientras Lucía cambia las fechas, el total se actualiza solo, sin recargar. routes/sitio.py y reservar.js para el total.
  3. Lucía escribe su nombre y confirma. No hay tarjeta: el pago es un ejemplo, se paga en el hotel. el formulario se manda con POST /reservar.
  4. La cocina revisa las reglas: que las fechas tengan sentido, que entren dos personas, y busca una habitación de ese tipo que no esté ocupada esas noches. Encuentra la 102. services/reservas.py: crear_reserva_web() y crear_reserva().
  5. Se guarda la reserva en la despensa y Lucía ve la página de confirmación con su código. se agrega una fila en la tabla reservas.
  6. En la recepción, Martín abre el plano y la 102 ya figura «Llega» el día 20. Nadie la cargó a mano: el plano mira las reservas cada vez que se abre. services/ocupacion.py calcula el estado de cada habitación.
  7. El día 20 llega Lucía. Martín toca la 102 y aprieta «Hacer check-in». Si la habitación estuviera sucia, el sistema le avisaría que primero hay que limpiarla. plano.js → /api/.../check-in → services/recepcion.py.

4

Las ideas importantes, con ejemplos

Estas son las decisiones que conviene saber explicar. Cada una tiene un ejemplo para contarla sin tecnicismos.

La ocupación no se guarda: se calcula

La habitación no tiene un casillero que diga «ocupada». El sistema mira las reservas de ese día y lo deduce.

Es como la edad: no anotás «tengo 17» porque cambia todos los años. Guardás la fecha de nacimiento y la edad se calcula. Acá se guardan las reservas y «ocupada» se calcula.

services/ocupacion.py

Dos reservas no se pueden pisar

Antes de guardar o mover una reserva se revisa que esa habitación no tenga otra esas noches. Salir y entrar el mismo día sí se puede.

Como un lugar de estacionamiento: uno se va a las 10 y el otro llega a las 14. El mismo día, pero no a la vez. Por eso en el tape chart cada día está partido en mañana (salida) y tarde (entrada).

reserva_superpuesta() en services/reservas.py

Se revisa dos veces: en la página y en el servidor

Cuando arrastrás una reserva, la página ya te avisa si pisa otra. Pero el servidor lo vuelve a revisar al guardar.

El mozo te dice «ese plato se terminó», pero la cocina igual se fija antes de cocinar. Alguien podría saltearse al mozo (por ejemplo, mandando el pedido a mano), así que la cocina no confía y revisa.

tapechart.js avisa · mover_reserva() decide

Marca blanca: el mismo sistema para cualquier hotel

Nombre, logo, color y textos se cargan desde Configuración. El color del texto de los botones (blanco o negro) se elige solo según lo claro que sea el color del hotel.

Como las franquicias: el local es el mismo, cambia el cartel. Si el hotel elige amarillo, los botones llevan letra negra; si elige azul oscuro, letra blanca, para que siempre se lea.

texto_sobre() en services/hotel.py

Login y permisos

La administración pide usuario y contraseña; el sitio público no. Hay dos roles: recepción y administración. Solo administración entra a Configuración.

En un hotel, el recepcionista tiene llave de las habitaciones pero no de la oficina del dueño. Acá pasa lo mismo con las pantallas.

routes/auth.py: login_requerido() y admin_requerido()

La contraseña no se guarda tal cual

Se guarda un «hash»: una versión transformada de la que no se puede volver atrás. Al ingresar, se transforma lo que escribiste y se compara.

Como una huella digital: el sistema no guarda tu dedo, guarda la huella. Puede comprobar que sos vos, pero con la huella no se puede fabricar el dedo.

set_password() y check_password() en models/usuario.py

Páginas que se actualizan sin recargar

En el plano, el tape chart y la nueva reserva, el JavaScript le pide datos al servidor y cambia solo un pedazo de la página.

Como un tablero de aeropuerto que cambia una línea cuando un vuelo se demora, en vez de reimprimir todo el tablero.

routes/api.py (responde en JSON) · static/js/

Cuando algo no se puede, el sistema explica por qué

Todas las reglas usan el mismo aviso, ErrorDeNegocio, con un mensaje pensado para la persona: «La 204 está sucia. Marcala como limpia antes del check-in».

Es la diferencia entre un cajero que dice «error» y uno que dice «no tenés saldo suficiente».

services/errores.py

Las habitaciones en 3D

Se armaron en Blender con muebles gratuitos, y la luz se «horneó» dentro del modelo. El navegador solo tiene que mostrarlo, sin calcular luces.

Como una maqueta ya pintada con sombras: se ve bien desde cualquier ángulo y no hace falta iluminarla con lámparas.

design/3d/ · archivos .glb · model-viewer

Las pruebas automáticas

Hay 98 pruebas que revisan solas que las reglas sigan funcionando, por ejemplo que no se pueda reservar una habitación ocupada.

Como un checklist antes de despegar: cada vez que se cambia algo se corre la lista entera, y si algo se rompió se nota enseguida.

6

Preguntas que te puede hacer el profe

Respuestas cortas para tener a mano. Tocá cada pregunta para abrirla.

¿Dónde se guarda si una habitación está ocupada?

En ningún lado, a propósito. Se guardan las reservas y el estado se calcula cada vez (services/ocupacion.py). Si se guardara aparte, podría quedar desactualizado: por ejemplo, cancelan una reserva y alguien se olvida de liberar la habitación.

¿Qué pasa si dos personas reservan la misma habitación las mismas noches?

Antes de guardar, reserva_superpuesta() busca si hay otra reserva activa de esa habitación cuyas fechas se crucen. Si la hay, no se guarda y se muestra un mensaje. En la web, el sistema directamente busca otra habitación libre del mismo tipo.

¿Por qué separaron rutas y servicios?

Porque la misma regla se usa desde lugares distintos. Crear una reserva se hace desde el sitio web y desde la administración, y las dos usan la misma función crear_reserva(). Si la regla estuviera dentro de cada ruta, habría que escribirla dos veces y mantenerlas iguales.

¿Cómo sabe el sistema que estoy logueado?

Al ingresar, Flask guarda tu número de usuario en la sesión, que es una cookie firmada con una clave secreta (está en .env). Si alguien la modifica, la firma no coincide y no sirve. Antes de cada página de la administración, login_requerido() se fija si hay alguien en la sesión.

¿Qué es un blueprint?

Un grupo de páginas de una misma sección. Hay uno para el sitio público, uno para el plano, uno para reservas, uno para configuración, etcétera. Sirve para no tener todas las URLs en un solo archivo enorme, y para decir de una vez «todo este grupo pide login».

¿Por qué Flask y SQLite?

Flask es chico y deja ver cómo funciona cada pedido, sin magia escondida. SQLite es una base de datos que vive en un solo archivo y no necesita instalar un servidor aparte. Si un hotel la necesitara más grande, se cambia a PostgreSQL desde DATABASE_URL sin tocar el código.

¿Qué APIs o servicios externos usan?

Google Maps para el mapa del hotel (se inserta con un link, sin clave), Google Fonts para la letra Inter y la librería model-viewer de Google para mostrar los modelos 3D (guardada dentro del proyecto). Además, la administración tiene su propia API interna en JSON (routes/api.py) que usa el JavaScript.

¿Es seguro?

Para un trabajo escolar tiene lo básico bien hecho: contraseñas con hash, sesión firmada, la configuración solo para administración, el JavaScript nunca toca la base, y los archivos subidos se revisan (que una «imagen» sea de verdad una imagen y no pese demasiado). Para un hotel real faltaría, por ejemplo, HTTPS y límite de intentos de login.

¿Qué hicieron con inteligencia artificial y qué ustedes?

Respondé con la verdad de cómo trabajaste. Una forma de contarlo: las decisiones (qué hace el sistema, que sea para vender a hoteles, cómo se reserva, el diseño de las pantallas en Google Stitch, los modelos en Blender) las tomaste vos, y usaste IA como ayuda para escribir y revisar el código. Lo importante es poder explicar cada parte, y para eso está esta guía.

¿Qué le agregarían después?

Cancelar y editar reservas, la sección de Huéspedes (está marcada como «Pronto»), pagos reales con una pasarela de pago, reportes de ocupación por mes, y que una sola instalación sirva para varios hoteles a la vez.

8

Cómo correrlo

iniciar.bat

Doble clic. La primera vez prepara Python e instala las librerías (necesita internet). Después pregunta si querés recargar los datos de ejemplo con la fecha de hoy, levanta el servidor y abre la página.

  • Sitio: http://127.0.0.1:5000/
  • Administración: /administracion
  • Para cortarlo: cerrar la ventana negra.

guia-de-estudio.bat

Abre esta guía y el mapa del código. No necesita internet ni que el servidor esté andando.

  • Mapa: docs/mapa-del-codigo.html
  • Guía: docs/guia-de-estudio.html

Si algo falla

  • «No se encontró Python»: instalarlo desde python.org tildando «Add python.exe to PATH».
  • El puerto 5000 está ocupado: cerrar la otra ventana del servidor.
  • Las reservas están viejas: correr iniciar.bat y responder S para recargar.
  • Correr las pruebas: .venv\Scripts\python -m pytest
